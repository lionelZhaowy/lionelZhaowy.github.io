## Project Background
This project focuses on developing a companion AI model compilation and deployment toolchain for an iteratively upgraded `2D/3D image-compatible SIMD vision chip` (see [[Chip Paper Link]](https://ieeexplore.ieee.org/abstract/document/10361842)[[Chip Paper PDF]](/images/project/202604-202606-S28Compiler/A_Real-Time_2D_3D_Perception_Visual_Vector_Processor_for_1920__1080_High-Resolution_High-Speed_Intelligent_Vision_Chips.pdf)[[Packaging Paper Link]](https://iopscience.iop.org/article/10.1088/1674-4926/25010030/meta)[[Packaging Paper PDF]](/images/project/202604-202606-S28Compiler/A_2D3D_Vision_Chip_based_on_Organic_Substrate_3D_Package0122.pdf)). It aims to address the inefficiencies and error-prone nature of manual assembly programming with a custom instruction set, which was previously mandatory for executing network inference in the absence of a complete toolchain.

Building upon the previous framework ([Compilation and Deployment Toolchain for Custom Systolic Array Processors]({{ '/projects/202407-202510-infra/#infra_tag' | relative_url }})), I deeply refactored the compiler's front-end scheduling and back-end generation modules to suit the distinct characteristics of this SIMD processor architecture. The primary enhancements include:
- **Front-End Abstraction and Memory Scheduling**:
  - *Operator Decoupling*: Separated the Pooling and Resize operations from the tightly-coupled Conv-BN-ReLU fused operators used in the legacy systolic array, delegating them to the vector core for independent assembly implementation.
  - *Conflict-Free Address Mapping*: Enforced strict compliance with the dual-zone independent read/write constraints of the vision processor data memory (VPDM) to achieve static memory allocation across input features, network parameters, and output results.
- **Back-End Generation and Operator Library**:
  - *Tensor Dimension Rearrangement*: Rearranged parameters like weights and biases during compile time to align with the "row-interleaved" physical memory format mandated by the vector processor.
  - *Assembly Operator Library*: Programmed highly optimized assembly templates for operators matching different reconfigurable PE grouping (PEG) modes.
  - *Automated Generation*: Linked the front-end parsed computational graph with allocated memory addresses to automatically instantiate operator templates, producing binary parameter files and assembly code for end-to-end network inference.

  <summary>1. Hardware Platform: Custom SIMD Vision Chip Microarchitecture</summary>
  <div class="tech-accordion-content" markdown="1">

Compared to its first-generation predecessor, the new SIMD chip exhibits significant upgrades in both process technology and architecture:
- *Enhanced Compute Density*: Fabricated in a 28nm process with a core frequency scaled to 600 MHz. Custom extension instructions double the density of the AI MAC units within the vector core, unleashing a peak performance of 2.2 TOPS.
- *Ring Topology Interconnect*: The processing element (PE) array is physically connected head-to-tail to form a ring topology, facilitating seamless data rotation across boundaries.
- *Multi-Die Distributed Scaling*: Integrates high-speed SERDES interfaces to support low-latency inter-chip communication and distributed inference for large-scale models.

#### 1.1. Vector Core Architecture
The vector core comprises a scalar unit and a vector unit. The vector unit incorporates 256 PEs, where each PE can access the local registers of its two immediate neighbors. The array can be dynamically reconfigured into six PE Group (PEG) modes (`PEG256×1`, `PEG128×2`, `PEG64×4`, `PEG32×8`, `PEG16×16`, and `PEG8×32`). The vector core pipeline is illustrated in Figure 1, and examples of PEG configurations are shown in Figures 2 and 3.

#### 1.2. Memory Hierarchy and Access Interfaces
The vector core integrates a Vision Processor Data Memory (VPDM) alongside multi-type register files. It handles data operations via a variable-granularity memory interface, forming a hierarchical storage architecture.

Register File (RF) Categories:
- *Scalar Regfile (SRF)*: Comprises 32 32-bit registers within the scalar unit, typically utilized for branch flags, address pointers, and global parameters.
- *Global Regfile (GRF)*: Comprises 16 32-bit registers per PEG within the vector unit, generally used to store weights shared by all PEs within that PEG.
- *Local Regfile (LRF)*: Comprises 16 16-bit registers per PE within the vector unit, typically holding input feature map data.
- *AI Regfile (ARF)*: Comprises 8 32-bit accumulators per PE within the vector unit, dedicated to staging the partial sums computed by `aimac` instructions.

The VPDM architecture, depicted in Figure 4, is composed of two groups of SRAM modules, each containing 16 128-bit wide, 8192-deep banks, accumulating a total capacity of 4 MB. Due to the structural constraints of the group selection design, the core can only perform concurrent read/write operations on different groups simultaneously. This necessitates compiler-level orchestration to avoid access conflicts resulting from concurrent access to the same group.

#### 2.1. Convolution Mapping
Tailored to the characteristics of the SIMD array, spatial dimension computations are mapped directly to the PE array: columns of the input feature map are mapped to PE indices (e.g., column 3 maps to PE3), rows are mapped to the LRF indices within each PE (e.g., row 1 maps to LRF1 across all PEs), and weights are broadcast to the GRF of the PEG. The convolution loop structure corresponding to this mapping strategy is shown in Figure 7.

<div align="center">
    <img src="/images/project/202604-202606-S28Compiler/loops_Conv.png" width="85%" alt="Figure 7">
    <br>
    <div style="color: #666; font-size: 14px; padding-top: 5px;">
        <b>Figure 7.</b> Convolution loop hierarchy
    </div>
</div>

As illustrated in Figure 7, the convolution mapping on the vector core features the following properties:
- *Array-Matched Tiled Computation*: To match the physical dimensions of the PE array and the number of channels processed per PE, tiling is enforced across both output channels and spatial rows.
- *Inner Loop Parallel Unrolling*: Output feature columns map to PE indices and output rows correspond to the internal LRF registers, realizing data-level parallelism via loop unrolling in the inner loops.
- *Outer Loop Output-Stationary (OS) Dataflow*: Embraces an output-stationary dataflow where the outermost loop iterates over output channels, reusing the registers until the accumulation of partial sums is fully completed before writing back the results.

The inner loop invokes the custom `aimac42ex` instruction to execute multiply-accumulate operations, utilizing data from neighboring PEs to compute 4 rows of output features for 2 output channels simultaneously in a single operation, as demonstrated in Figure 8.

For a 3×3 convolution, the operation is fulfilled via nine consecutive `aimac42ex` instructions:
```text
aimac42ex lr1, lr3, gr1(lhw), d(l1) //Step=1
aimac42ex lr1, lr3, gr1(hhw)        //Step=2
aimac42ex lr1, lr3, gr2(lhw), d(h1) //Step=3
aimac42ex lr2, lr4, gr2(hhw), d(l1) //Step=4
aimac42ex lr2, lr4, gr3(lhw)        //Step=5
aimac42ex lr2, lr4, gr3(hhw), d(h1) //Step=6
aimac42ex lr3, lr5, gr4(lhw), d(l1) //Step=7
aimac42ex lr3, lr5, gr4(hhw)        //Step=8
aimac42ex lr3, lr5, gr5(lhw), d(h1) //Step=9
```

The outer loops employ counters to traverse input channels (loop 1), output rows (loop 2), and output channels (loop 3), repeatedly calling the inner loop to finalize 4 rows of output feature maps for 2 output channels at a time, ultimately computing the entire feature map.

*Utilization Optimization*: When the dimensions of the feature map are small, the vector unit can be reconfigured to enable inter-PEG channel parallelism to enhance compute unit utilization. For instance, with a 64×64 input feature map (Figure 9), the vector unit can be dynamically reconfigured into a parallel `PEG64×4` structure.

*Row-Interleaved Data Arrangement*: Because multi-PEG parallel computation causes the physical layout of feature maps on-chip to assume a "row-interleaved" pattern, a feature map logically formatted as $(W,H,C)$ is physically stored on-chip as $(W, \#PEG, H, C/\#PEG)$. This configuration mandates a corresponding data rearrangement of model parameters: weights logically formatted as $(K,K,C_{in},C_{out})$ are rearranged into $(2,\#PEG,k,k,C_{in},C_{out}/T_{co})$, and biases logically formatted as $(C_{out})$ are rearranged into $(2,\#PEG,C_{out}/T_{co})$.

## Reflections and Summary

### Personal Evaluation: From Coarse-Grained Scheduling to Fine-Grained Programming

Developing this compilation and deployment toolchain provided a firsthand appreciation of the profound paradigm shifts across diverse hardware architectures. In contrast to preceding projects—such as the [legacy NNA from my undergraduate thesis]({{ '/projects/202312-202405-graduation/#graduate_tag' | relative_url }}) and the [next-generation NNA with CNN-Transformer support]({{ '/projects/202407-202510-infra/#infra_tag' | relative_url }})—which relied on coarse-grained configuration register words to drive systolic array inference acceleration, programming for SIMD vector cores is highly fine-grained, demanding explicit instruction-level coding for every computational step. While this paradigm yields superior versatility and flexibility over coarse-grained configuration, allowing for the execution of arbitrary non-linear operators and legacy computer vision algorithms, it forfeits the innate data-reuse benefits of systolic arrays. Consequently, the actual compute utilization efficiency hinges heavily on the compiler's capability to orchestrate instruction scheduling and optimize execution pipeline throughput.

### Bottleneck Analysis: The Memory Access Predicament of Single-Threaded SIMD

Physical board-level evaluation revealed an explicit performance bottleneck: despite the new SIMD processor's peak compute capacity (2.2 TOPS) substantially outstripping that of the systolic array (1.4 TOPS), its measured frame rate under the CenterNet network (less than 160 FPS) lagged significantly behind the systolic array architecture (375 FPS).

The root cause of this performance discrepancy resides in the memory-bounded nature imposed by fine-grained SIMD programming. Due to the complete absence of a hardware-level context switching mechanism, granular calculation sequences force the processing cores to frequently stall while awaiting the resolution of `Load/Store` instructions. This severely depresses the actual arithmetic intensity, causing execution units to sit idle.

**Proposed Solutions**:

* *Software Optimization: Re-orchestrating Assembly via Dual-Issue Pipelining*: Given that the hardware configuration of the current-version SIMD vector processor is immutable, optimization must be pursued strictly at the software inference function layer. By maximizing the dual-issue mechanism and introducing register-level ping-pong buffering, data required for the subsequent iteration can be concurrently loaded during current-cycle computation, successfully achieving memory latency hiding.
* *Next-Generation Hardware Enhancements: Transitioning from Single-Threaded SIMD to SIMT*: Future microarchitectural iterations should integrate hardware-level multi-threading capabilities. Incorporating a hardware scheduler would allow the core to instantly switch to a thread with ready data whenever the active thread stalls on memory access, ensuring compute units remain continuously saturated and achieving full compute-memory overlap.

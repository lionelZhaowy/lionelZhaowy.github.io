## Project Background
This project developed an AI compilation and deployment toolchain for an upgraded `SIMD vision chip supporting both 2D and 3D imaging` (see the [[chip paper]](https://ieeexplore.ieee.org/abstract/document/10361842), [[chip paper PDF]](/images/project/202604-202606-S28Compiler/A_Real-Time_2D_3D_Perception_Visual_Vector_Processor_for_1920__1080_High-Resolution_High-Speed_Intelligent_Vision_Chips.pdf), [[packaging paper]](https://iopscience.iop.org/article/10.1088/1674-4926/25010030/meta), and [[packaging paper PDF]](/images/project/202604-202606-S28Compiler/A_2D3D_Vision_Chip_based_on_Organic_Substrate_3D_Package0122.pdf)). Before this toolchain was available, each network had to be implemented manually in the processor's custom assembly language—an inefficient and error-prone workflow.

Building on the earlier [toolchain for a custom systolic-array processor]({{ '/projects/202407-202510-infra/#infra_tag' | relative_url }}), I refactored both front-end scheduling and back-end code generation for the SIMD architecture:
- **Front-End Abstraction and Memory Scheduling**:
  - *Operator decoupling*: Separated Pooling and Resize from the Conv–BN–ReLU fusion pattern used by the earlier systolic-array compiler and implemented them as independent vector-core operators.
  - *Conflict-free address mapping*: Added static allocation of activations, parameters, and outputs under the VPDM constraint that simultaneous reads and writes must target different memory groups.
- **Back-End Generation and Operator Library**:
  - *Tensor layout transformation*: Reordered weights and biases at compile time to match the processor's row-interleaved physical layout.
  - *Assembly operator library*: Implemented optimized templates for the supported reconfigurable PE-group (PEG) modes.
  - *Automated generation*: Bound parsed graph nodes and allocated addresses to the appropriate templates, emitting binary parameter images and assembly programs for complete-network inference.

  <summary>1. Hardware Platform: Custom SIMD Vision Chip Microarchitecture</summary>
  <div class="tech-accordion-content" markdown="1">

Relative to the first-generation design, the new SIMD chip incorporates several process and architectural enhancements:
- *Higher compute density*: The 28 nm implementation operates at up to 600 MHz, while custom instructions double the density of AI MAC units in the vector core, providing 2.2 TOPS peak throughput.
- *Ring-connected PE array*: The first and last processing elements are physically connected, enabling data rotation across the array boundary.
- *Multi-chip scalability*: High-speed SERDES interfaces support low-latency chip-to-chip communication and distributed execution of larger models.

#### 1.1. Vector Core Architecture
The vector core contains scalar and vector execution units. The vector unit comprises 256 PEs; each PE can access the local registers of its two neighboring PEs. The array supports six PE-group (PEG) configurations: `PEG256×1`, `PEG128×2`, `PEG64×4`, `PEG32×8`, `PEG16×16`, and `PEG8×32`. Figure 1 shows the pipeline, and Figures 2 and 3 illustrate representative PEG modes.

The scalar and vector units share the first two pipeline stages. During instruction line-up (IL), instructions are dispatched by type through a `dual-issue` mechanism, allowing scalar and vector instructions to execute in parallel.

#### 1.2. Memory Hierarchy and Access Interfaces
The vector core combines the Vision Processor Data Memory (VPDM) with several classes of register file and a variable-granularity load/store interface.

Register-file classes:
- *Scalar register file (SRF)*: 32 32-bit registers in the scalar unit, used for branch conditions, address pointers, and global parameters.
- *Global register file (GRF)*: 16 32-bit registers per PEG, typically holding weights shared across the PEs in that group.
- *Local register file (LRF)*: 16 16-bit registers per PE, typically holding activation data.
- *AI register file (ARF)*: Eight 32-bit accumulators per PE for partial sums generated by `aimac` instructions.

As shown in Figure 4, the 4 MB VPDM comprises two SRAM groups. Each group contains 16 banks, with each bank organized as 8192×128 bits. The port-selection logic permits concurrent reads and writes only when they address different groups, so the compiler must allocate operands to avoid same-group access conflicts.

#### 2.1. Convolution Mapping
Convolution is spatially mapped onto the SIMD array: feature-map columns correspond to PE indices (for example, column 3 maps to PE3), rows correspond to LRF indices within each PE, and weights are broadcast through the PEG's GRF. Figure 7 shows the resulting loop hierarchy.

<div align="center">
    <img src="/images/project/202604-202606-S28Compiler/loops_Conv.png" width="85%" alt="Figure 7">
    <br>
    <div style="color: #666; font-size: 14px; padding-top: 5px;">
        <b>Figure 7.</b> Convolution loop hierarchy
    </div>
</div>

The mapping has three principal characteristics:
- *Array-aligned tiling*: Output channels and rows are tiled to match the PE-array dimensions and the number of channels processed by each PE.
- *Spatial loop unrolling*: Output columns map across PEs and output rows across LRF entries, exposing data-level parallelism in the inner loop.
- *Output-stationary dataflow*: Partial sums remain in the accumulator registers until all contributing input channels have been processed, after which the completed outputs are written back.

The inner loop uses the custom `aimac42ex` instruction and neighboring-PE register accesses to compute four output rows for two output channels in parallel (Figure 8).

One 3×3 convolution step is expressed as nine consecutive `aimac42ex` instructions:
```text
aimac42ex lr1, lr3, gr1(lhw), d(l1) //Step=1
aimac42ex lr1, lr3, gr1(hhw)        //Step=2
aimac42ex lr1, lr3, gr2(lhw), d(h1) //Step=3
aimac42ex lr2, lr4, gr2(hhw), d(l1) //Step=4
aimac42ex lr2, lr4, gr3(lhw)        //Step=5
aimac42ex lr2, lr4, gr3(hhw), d(h1) //Step=6
aimac42ex lr3, lr5, gr4(lhw), d(l1) //Step=7
aimac42ex lr3, lr5, gr4(hhw)        //Step=8
aimac42ex lr3, lr5, gr5(lhw), d(h1) //Step=9

```

The surrounding loops iterate over input channels (loop 1), output rows (loop 2), and output channels (loop 3), repeatedly invoking the inner kernel until the complete output feature map has been generated.

*Utilization optimization*: For narrow feature maps, the vector unit can be divided into multiple PEGs that process channels in parallel. A 64×64 input, for example, can use the `PEG64×4` configuration shown in Figure 9.

*Row-interleaved layout*: Multi-PEG execution stores a logical feature map $(W,H,C)$ physically as $(W,\#PEG,H,C/\#PEG)$. The compiler applies the corresponding parameter transformations: weights from $(K,K,C_{in},C_{out})$ to $(2,\#PEG,K,K,C_{in},C_{out}/T_{co})$, and biases from $(C_{out})$ to $(2,\#PEG,C_{out}/T_{co})$.

The example in Figure 10 requires 12 consecutive multiply–accumulate steps:

```text
aimulg  air1,lr1,gr1(lhw);        // Step=1, 
aiadd2; aimulg  air1,lr2,gr1(hhw) // Step=2,  
aiadd2; aimulg  air1,lr3,gr2(lhw) // Step=3,  
aiadd2; aimulg  air1,lr4,gr2(hhw) // Step=4, Row 1 completed
aimulg  air1,lr1,gr3(lhw);        // Step=5, 
aiadd2; aimulg  air1,lr2,gr3(hhw) // Step=6,  
aiadd2; aimulg  air1,lr3,gr4(lhw) // Step=7,  
aiadd2; aimulg  air1,lr4,gr4(hhw) // Step=8, Row 2 completed
aimulg  air1,lr1,gr5(lhw);        // Step=9, 
aiadd2; aimulg  air1,lr2,gr5(hhw); // Step=10, 
aiadd2; aimulg  air1,lr3,gr6(lhw); // Step=11, 
aiadd2; aimulg  air1,lr4,gr6(hhw); // Step=12, Row 3 completed

```

The outer loops iterate over output rows (loop 1) and reduction-dimension rows (loop 2), repeatedly invoking the vector–scalar inner kernel to construct the complete output matrix.

*Utilization optimization*: When matrix B has relatively few columns, multiple PEGs can process different output rows concurrently. For $A(32,128)\times B(128,64)=C(32,64)$, the vector unit can use `PEG64×4`.

## Reflections and Summary

### Personal Evaluation: From Coarse-Grained Scheduling to Fine-Grained Programming

This toolchain highlighted the programming-model difference between systolic arrays and SIMD processors. The [first-generation NNA used in my undergraduate thesis]({{ '/projects/202312-202405-graduation/#graduate_tag' | relative_url }}) and the [later CNN–Transformer NNA]({{ '/projects/202407-202510-infra/#infra_tag' | relative_url }}) were controlled through coarse-grained configuration words. By contrast, the SIMD vector core requires explicit instruction-level scheduling of each computational step. This fine-grained model supports a broader range of nonlinear operators and conventional vision algorithms, but it does not inherit the systolic array's implicit data reuse. Sustained utilization therefore depends strongly on compiler scheduling, register allocation, and pipeline-aware code generation.

### Bottleneck Analysis: The Memory Access Predicament of Single-Threaded SIMD

Board-level measurements exposed a clear bottleneck. Although the SIMD processor provides 2.2 TOPS peak throughput compared with 1.4 TOPS for the systolic-array design, CenterNet ran at fewer than 160 FPS on the SIMD processor versus 375 FPS on the systolic array.

Fine-grained SIMD execution made the workload memory-bound. Because the core provides no hardware context switching, instruction sequences frequently stall on `Load/Store` operations, lowering effective arithmetic intensity and leaving execution units idle.

**Proposed Solutions**:

* *Software: dual-issue scheduling and register double buffering*: Reorder assembly to exploit scalar–vector dual issue and preload the next iteration's data into an alternate register set while the current iteration computes, thereby hiding part of the memory-access latency.
* *Hardware: transition from single-threaded SIMD toward SIMT*: A future design could add hardware multithreading so that the scheduler switches to a ready thread when the active thread stalls on memory, improving overlap between data movement and computation.

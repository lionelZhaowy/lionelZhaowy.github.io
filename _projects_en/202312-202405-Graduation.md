## Project Background
A vision chip integrates sensing, memory, and computation into an edge system-on-chip (SoC), reducing data-transfer bottlenecks and enabling low-latency visual processing near the sensor. Its compute and storage resources are nevertheless constrained by strict power and silicon-area budgets, making conventional object-tracking networks difficult to deploy directly.

This undergraduate thesis developed a single-object tracking algorithm tailored to a vision processor designed by our research group and completed the full workflow of model design, compression, compilation, and on-chip deployment.

<details class="tech-accordion" markdown="1">
  <summary>1. Processor Constraints</summary>
  <div class="tech-accordion-content" markdown="1">

The target platform comprises an image sensor and a readout/processor die developed by our research group. The readout circuitry and processor are fabricated on the same die and integrated with the sensor through 3D stacking to form the complete vision SoC.

The processor uses a heterogeneous architecture with three compute engines:
- **MPU**: A microcontroller based on the MIPS instruction set, responsible for executing the global main function, scheduling data transfers, and controlling the activation/deactivation of the heterogeneous cores.
- **Vector Processor (VP)**: A vector processor based on a custom instruction set, tasked with vector operations and data rearrangement.
- **NN Processor (NNP)**: A custom-developed systolic array accelerator compatible with "Convolution-GEMM" operations ([[Paper]](https://ietresearch.onlinelibrary.wiley.com/doi/full/10.1049/ell2.13125)[[pdf]](/images/project/202312-202405-Graduation/Electronics%20Letters%20-%202024%20-%20Wang%20-%20A%20Conv‐GEMM%20reconfigurable%20accelerator%20with%20WS‐RS%20dataflow%20for%20high%20throughput.pdf)), specifically designed to accelerate compute-intensive tasks within neural networks.

Model deployment must satisfy three primary hardware constraints:
- **Operator support**: The NNP supports only selected convolution configurations and pooling windows; it does not support activation functions other than ReLU or quantized matrix multiplication. Unsupported operators must therefore be avoided or reformulated.
- **On-chip memory capacity**: To prioritize energy-efficient on-chip execution, the chip has no external-memory interface. All parameters and intermediate feature maps must fit within the 4 MB global data memory (DM).
- **Arithmetic precision**: The processor implements an integer-only W8A8B16 datapath—INT8 weights and activations with INT16 biases. Its 24-bit accumulator is saturated and narrowed to INT16 before multiply–shift requantization, so the quantization model must reproduce these arithmetic semantics accurately.

#### 2.1. SiamVC Network Architecture
Because the chip's operator library supports only CNN-based models, SiamVC (Siamese Network for Vision Chip) adopts an efficient Siamese tracking architecture. As shown in Figure 1, the template and search branches share the backbone function $\phi$:
- Template Branch: Inputs a target image $z$ with a resolution of 128×128.
- Tracking Branch: Inputs a search region $x$ with a resolution of 256×256.

The two feature maps are combined by pointwise cross-correlation $f$ to produce the similarity map $s=f(\phi(z),\phi(x))$. This map is then processed by a foreground/background classification branch $g_{cls}$ and an `ltrb` bounding-box regression branch $g_{ltrb}$, producing $g_{cls}(s)$ and $g_{ltrb}(s)$.

SiamVC includes three hardware-oriented design choices:
- A streamlined MobileNetV2 backbone ensures that every operator is supported by the hardware.
- An anchor-free head based on depthwise separable convolution avoids complex post-processing such as non-maximum suppression (NMS), which maps poorly to the systolic array.
- Matrix multiplications in the cross-correlation stage are reformulated as NNP-supported 1×1 convolutions.

SiamVC occupies only 325 kB and requires 0.11 GOPS, satisfying the target platform's deployment constraints.

#### 2.2. Knowledge Distillation Based on Output Features
To recover accuracy lost through aggressive model compression and low-bit quantization, I introduced the output-feature distillation scheme shown in Figure 2. A larger teacher, SiamVC-T, supervises the student SiamVC-S through the mean-squared error (MSE) between their output features.

The total loss function is formulated as a weighted sum of the hard loss (Cross-Entropy and IoU losses) and the soft loss:
- Total Loss: $L_{total}=\alpha L_{hard}+(1-\alpha)L_{soft}$
- Hard Loss: $L_{hard}=L_{CE}+L_{IOU}$
  - Foreground-Background Classification Cross-Entropy: $L_{CE}(p,q)=-\sum p(x)\log (q(x))$
  - Coordinate Regression IoU Loss: $L_{IOU}(A,B)=1-IOU=1-\frac{A\cap B}{A\cup B}$
- Soft Loss: $L_{soft}=L_{MSE_{cls}}+L_{MSE_{loc}}$
  - Feature-Level MSE Loss: $L_{MSE}(G,Y)=\frac{1}{N}\sum\limits_{i=1}^{N}(G_{i}-Y_{i})^{2}$

<details class="tech-accordion" markdown="1">
  <summary>3. Compilation and Deployment Toolchain</summary>
  <div class="tech-accordion-content" markdown="1">

Deployment uses the custom vision-chip toolchain shown in Figure 5:
- **Model quantization**: Parses ONNX models, performs post-training quantization (PTQ), and emits operator descriptions and parameters in the chip-specific format.
- **Algorithm-level verification**: Models the integer-only datapath in MATLAB to estimate hardware accuracy and provide a golden reference for VCS simulation.
- **Compiler front end**: Performs graph transformations such as operator fusion, aggregates node metadata, and allocates memory.
- **Compiler back end**: Generates the C entry point for MPU scheduling and the configuration-register stream for the NNP array.
- **(Optional) VP Assembly**: For unsupported non-linear operators or specific data rearrangement logic, handwritten VP assembly programs are required.
- **RTL Simulation Verification**: Cross-compiles MCU/VP/NNP programs into binaries for VCS simulation, comparing the computational outcomes.
- **Board-Level Testing**: Following successful RTL simulation, the programs are flashed onto the vision chip test board for physical evaluation.

## Reflections and Summary
### Personal Evaluation: From Dedicated Accelerators to Programmable Processors
Unlike the fixed-function AOD-Net accelerator developed in the [Benxin Program]({{ '/projects/202305-202309-microhfut/#micro_tag' | relative_url }}), this project targeted a programmable processor. It demonstrated that the practical usability of an architecture depends strongly on the maturity of its compiler toolchain. VP assembly programming and NNP configuration still required substantial manual effort, creating a high barrier to deployment. A robust compiler is therefore more than an interface between a model and the hardware: it is essential to the productivity and commercial viability of the processor.

### Hardware-Software Co-Design: Hardware-Aware Compression for Custom Processors
This work also showed that compression methods validated on CPUs or GPUs may not transfer directly to a custom processor, whose microarchitecture and arithmetic circuits impose substantially different constraints.

Compared with GPU inference, the on-chip predictions exhibited frame-to-frame bounding-box jitter. The cause was a mismatch in arithmetic semantics: the hardware saturates and narrows its 24-bit accumulator to INT16 before the multiply–shift stage, but this operation had not been modeled during training or quantization.

The result illustrates why a compressed model that performs well on a general-purpose platform can lose substantial accuracy after deployment on custom silicon. Closing the gap between idealized algorithmic arithmetic and the implemented datapath is therefore critical. In addition, custom processors constrain both the available operator set and on-chip SRAM capacity. Hardware-aware neural architecture search can explore model topologies within the supported operator space, while QAT must reproduce the hardware's exact bit-width, saturation, truncation, and rounding rules. Together, these techniques provide a practical route to genuine hardware–software co-design.

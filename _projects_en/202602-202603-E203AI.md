## Project Background
Traditional AI accelerators typically adopt loosely-coupled integration methods, such as heterogeneous multi-core architectures or memory-mapped configurations. Under such frameworks, the control core and the accelerator rely heavily on the system bus or a DMA controller for explicit data movement and task scheduling. This not only introduces exorbitant driver and interrupt handling overhead, but the frequent memory accesses also trigger a severe "memory wall" and power bottlenecks, failing to satisfy the rigorous demands of ultra-low-power edge scenarios.

Boasting open-source and highly extensible properties, the RISC-V Instruction Set Architecture (ISA) unlocks a **tightly-coupled design paradigm** for edge AI acceleration. By implementing custom extension instructions, a parallel computing array can be embedded directly as an execution unit into the EX (Execute) stage of the CPU pipeline. This fundamentally eradicates inter-core data interaction latency and drastically simplifies the software programming model.

Conceived as an independently explored "toy project," this endeavor aims to chart the microarchitectural evolution of highly energy-efficient AI MCUs through full-stack hardware-software co-design.

  <summary>1. RISC-V Custom Extension Instruction Set</summary>
  <div class="tech-accordion-content" markdown="1">

This project integrates a systolic array accelerator (Figure 2) via the NICE (Nuclei Instruction Co-unit Extension) coprocessor interface of the open-source Hummingbird E203 core (Figure 1). Its interface protocol natively supports the standard RISC-V `custom0-3` opcode space, providing an extensible foundation for a tightly-coupled architecture.

    </div>

Tailored to the computing characteristics of a systolic array using a Weight-Stationary (WS) dataflow, five custom extension instructions were engineered to span the full lifecycle of initialization, multiply-accumulate (MAC) operations, and result write-back:

| Instruction (`Inst`) | Register 1 (`rs1`) | Register 2 (`rs2`) | Functional Description (`Function`) |
| --- | --- | --- | --- |
| `sparam` | `{ReLU_en(1bit), sft(5bit), Mul(16bit)}` | - | Loads dequantization multiply-shift factors and ReLU activation configurations into the output processing unit. |
| `lybuf`  | `Bias_addr` | - | Loads biases into the accumulation registers of the PE array. |
| `lwbuf`  | `Weight_addr` | Column count of weight matrix | Loads weights into the internal registers of the PE array and fixes them stationary. |
| `matmul` | `Input_addr` | Column count of input matrix | Triggers diagonalized input matrix loading and systolic MAC operations, updating partial sums. |
| `sybuf`  | `Output_addr` | Column count of output matrix | Triggers dequantization calculations of the partial sums and writes the output features back to main memory. |

  <summary>4. Inference Driver and Compute Scheduling Implementation</summary>
  <div class="tech-accordion-content" markdown="1">

The software layer embraces a hierarchical design philosophy: **low-level extension instruction invocation** encapsulates hardware instructions via inline assembly, **mid-level operator implementation** orchestrates tile-based block computing for large-scale matrices, and **high-level network inference** executes the overall network pipeline.

- **Inline Assembly Encapsulation**: Instruction interfaces were constructed using C-language inline assembly within NucleiStudio (Figure 7).
- **Tile-Based Block Scheduling**: When operator dimensions exceed the physical scale of the systolic array hardware (e.g., 32×32), the software automatically performs tile partitioning and accumulation scheduling (Figure 8).
- **Network Inference Evaluation**: The main function schedules layer-by-layer inference in topological order and integrates a hardware timer for precise profiling of performance and instruction counts (Figures 9–11).

## FPGA Verification and Performance Evaluation
The tightly-coupled system was deployed and verified on a Xilinx Artix-7 A7-100t FPGA platform (Figure 12) with a 32×32 array scale. The evaluation inputs comprised 32 MNIST images with a 28×28 resolution (Figure 13), and the performance statistics were printed in real-time via a UART terminal (Figure 14).

### 1. Comprehensive Performance Metrics
At a 32×32 array scale, a benchmark comparison was conducted between the "custom instruction set-based coprocessor acceleration scheme" and a "pure scalar software execution scheme (C-language)":

| Evaluation Dimension | Pure Scalar Software Implementation (Baseline) | Extension Instruction Set Acceleration Scheme | Net Optimization Gain |
| :--- | :--- | :--- | :--- |
| **Instruction Count Overhead** | 14,374,915 instructions | **600 instructions** | **Reduced by 23,958x** |

## Reflections and Summary
### Personal Evaluation: From Loose Coupling to Instruction-Level Tight Coupling
This project represents my inaugural engineering practice in tightly-coupled AI acceleration architectures. Compared to traditional heterogeneous multi-core processors, a tightly-coupled microarchitecture based on RISC-V extension instructions unifies the programming model. Developers can accomplish intricate computation and control scheduling solely by leveraging a standard compilation toolchain within a bare-metal C environment, remarkably curtailing driver development and software abstraction overheads. Nonetheless, the current system targets matrix multiplication hardware acceleration, leaving a native lack of support for complex non-linear operators such as SoftMax and LayerNorm, which presents clear avenues for future optimization.

### Bottleneck Analysis: Bandwidth Constraints and Blocking Scheduling of the Coprocessor Interface
During the performance tuning phase, I identified that the bandwidth limits and blocking timing constraints of the Nuclei NICE interface acted as the definitive bottlenecks throttling the upper bound of computational throughput.

The optimal energy-efficiency state of a systolic array is a seamless, continuous flow of multiply-accumulate operations once the pipeline is fully saturated. However, because the NICE interface relies rigidly on in-order, single-instruction execution (lacking instruction-level parallelism and blocking the core pipeline), the system must wait for the current tile's compute instruction to completely finalize before issuing subsequent data-loading commands. This explicit synchronization between loading and computation induces periodic stalls across the array pipeline.

**Proposed Solutions**:
- *Deeply Customized Pipelined Architecture*: Sidestep the NICE interface entirely and insert a decoupled accelerator bypass directly after the EX stage of the CPU microarchitecture to establish a higher-bandwidth data interconnect, though this inherently increases RTL design complexity.
- *Introduction of Instruction Queue Decoupling (Decoupled Pipeline)*: Maintain the physical interface but introduce a command FIFO buffer queue. When the processor prefetches consecutive `load` and `compute` instructions, they are handed off to a queue management module to perform structural hazard checks, allowing the memory access pipeline and the array compute pipeline to execute concurrently via overlapping, thereby completely masking memory access latency.

In summary, this project realizes an end-to-end AI MCU, laying a solid foundation for the subsequent exploration of edge intelligence architectures capable of supporting complex operator pipelining and out-of-order scheduling.

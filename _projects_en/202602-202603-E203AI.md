## Project Background
Many AI accelerators are integrated as loosely coupled heterogeneous cores or memory-mapped peripherals. The host processor and accelerator then rely on a system bus or DMA engine for explicit data movement and task dispatch, introducing driver, synchronization, and interrupt overhead. Repeated movement through the memory hierarchy also increases latency and energy, which is particularly problematic in ultra-low-power edge systems.

The open and extensible RISC-V instruction-set architecture enables a **tightly coupled** alternative. Custom instructions allow a parallel compute array to be attached directly to the processor's execution path, reducing host–accelerator control overhead and presenting the accelerator through the conventional instruction-stream programming model.

This independently developed research prototype explored a full-stack hardware–software architecture for energy-efficient AI MCUs.

The systolic-array accelerator in Figure 2 is connected to the open-source Hummingbird E203 core (Figure 1) through the NICE (Nuclei Instruction Co-unit Extension) coprocessor interface. NICE supports the RISC-V `custom0–3` opcode spaces, providing the encoding and handshake mechanisms required for tight integration.

Five custom instructions were designed around the weight-stationary (WS) dataflow, covering configuration, data loading, multiply–accumulate execution, requantization, and result write-back:

| Instruction (`Inst`) | Register 1 (`rs1`) | Register 2 (`rs2`) | Functional Description (`Function`) |
| --- | --- | --- | --- |
| `sparam` | `{ReLU_en(1bit), sft(5bit), Mul(16bit)}` | - | Loads dequantization multiply-shift factors and ReLU activation configurations into the output processing unit. |
| `lybuf`  | `Bias_addr` | - | Loads biases into the accumulation registers of the PE array. |
| `lwbuf`  | `Weight_addr` | Column count of weight matrix | Loads weights into the internal registers of the PE array and fixes them stationary. |
| `matmul` | `Input_addr` | Column count of input matrix | Triggers diagonalized input matrix loading and systolic MAC operations, updating partial sums. |
| `sybuf`  | `Output_addr` | Column count of output matrix | Triggers dequantization calculations of the partial sums and writes the output features back to main memory. |

  <summary>4. Inference Driver and Compute Scheduling Implementation</summary>
  <div class="tech-accordion-content" markdown="1">

The software stack is organized into three layers: a low-level inline-assembly interface to the custom instructions, tiled matrix operators that map large workloads to the physical array, and a network-level runtime that sequences the complete inference graph.

- **Inline Assembly Encapsulation**: Instruction interfaces were constructed using C-language inline assembly within NucleiStudio (Figure 7).
- **Tile-Based Block Scheduling**: When operator dimensions exceed the physical scale of the systolic array hardware (e.g., 32×32), the software automatically performs tile partitioning and accumulation scheduling (Figure 8).
- **Network Inference Evaluation**: The main function schedules layer-by-layer inference in topological order and integrates a hardware timer for precise profiling of performance and instruction counts (Figures 9–11).

## FPGA Verification and Performance Evaluation
The tightly coupled system was implemented on a Xilinx Artix-7 A7-100T FPGA with a 32×32 PE array (Figure 12). The test workload contained 32 MNIST images at 28×28 resolution (Figure 13), and inference results and performance counters were reported over UART (Figure 14).

### 1. Comprehensive Performance Metrics
At a 32×32 array scale, a benchmark comparison was conducted between the "custom instruction set-based coprocessor acceleration scheme" and a "pure scalar software execution scheme (C-language)":

| Evaluation Dimension | Pure Scalar Software Implementation (Baseline) | Extension Instruction Set Acceleration Scheme | Net Optimization Gain |
| :--- | :--- | :--- | :--- |
| **Dynamic Instruction Count** | 14,374,915 instructions | **600 instructions** | **23,958× reduction** |
| **Execution Cycles** | 15,910,699 cycles | **37,577 cycles** | **423× speedup** |
| **Inference Accuracy (MNIST)** | 97.30% (FP32) | **97.26% (INT8 QAT)** | 0.04 percentage-point decrease |

## Reflections and Summary
### Personal Evaluation: From Loose Coupling to Instruction-Level Tight Coupling
This project was my first implementation of a tightly coupled AI accelerator. Compared with a loosely coupled heterogeneous design, exposing the accelerator through RISC-V instructions provides a unified programming model: computation and control can be expressed in bare-metal C using a conventional compiler toolchain, with far less driver and software-abstraction overhead. The current prototype accelerates matrix multiplication only, however, and provides no native support for nonlinear operators such as SoftMax or LayerNorm.

### Bottleneck Analysis: Bandwidth Constraints and Blocking Scheduling of the Coprocessor Interface
Performance analysis identified the bandwidth and blocking semantics of the Nuclei NICE interface as the principal limits on sustained array throughput.

A systolic array is most efficient when its pipeline remains filled with a continuous stream of multiply–accumulate operations. NICE executes these custom operations synchronously and blocks the in-order core, so software cannot issue the next tile's load while the current tile is being computed. This explicit load–compute serialization periodically drains the array pipeline.

**Proposed Solutions**:
- *Decoupled accelerator datapath*: Replace NICE with a dedicated, higher-bandwidth accelerator path after the CPU EX stage. This provides greater scheduling freedom at the cost of substantially more invasive RTL changes.
- *Queued command interface*: Retain the coprocessor connection but add a command FIFO and hazard-management logic. Buffered `load` and `compute` commands could then overlap memory transfers with array execution and hide a significant fraction of the data-loading latency.

Overall, the project demonstrates an end-to-end AI MCU prototype and provides a basis for future work on pipelined nonlinear operators, decoupled execution, and out-of-order accelerator scheduling.
